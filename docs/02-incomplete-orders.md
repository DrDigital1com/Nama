# אבחון הזמנות לא מושלמות — פלייבוק מלא

> זהו המסמך המרכזי. לעבוד לפי הסדר. כל שלב מסתיים בהחלטה: "זו הסיבה" או "לא זו — לשלב הבא".

---

## שלב 0: להגדיר מה בעצם "לא מושלם"

לפני כל אבחון — לוודא שמודדים את הדבר הנכון. ווקומרס מייצרת כמה סטטוסים שנראים כמו כשל אבל אינם:

| סטטוס | משמעות | האם זו תקלה? |
|---|---|---|
| `checkout-draft` | נוצר אוטומטית ע"י צ׳קאאוט הבלוקים בכניסה לעמוד, לפני כל ניסיון תשלום | **לא.** רעש. יש לנקות תקופתית |
| `pending` | הזמנה נוצרה, טרם התקבל תשלום | **תלוי בגיל.** עד שעה — תקין. מעל 24 שעות — תקלה |
| `failed` | התשלום נדחה או שהשער החזיר שגיאה | **כן**, אם השיעור גבוה |
| `on-hold` | ממתין לתשלום ידני (העברה בנקאית / צ׳ק) | **לא**, אם זו שיטת התשלום |
| `cancelled` | בוטל ידנית או אוטומטית אחרי אי-תשלום | **לא.** זו התנהגות תקינה של המערכת |

**נקודת ייחוס:** בחנות ישראלית תקינה עם סליקת אשראי, `pending + failed` מהווים בדרך כלל **8–15%** מכלל ההזמנות שהוכרעו. מעל **25%** — כמעט תמיד תקלה טכנית, לא נטישה טבעית.

הרצה: `sql/orders-diagnostics.sql` בדיקות A1 + A5 (או B1).

## שלב 1: הבדיקה שפותרת את רוב המקרים — "האם הלקוחות שילמו?"

זו הבדיקה החשובה ביותר. היא מפרידה בין שתי בעיות שונות לחלוטין.

הרצה: **בדיקה A7** (או B4) ב-`sql/orders-diagnostics.sql`.

השאילתה מחפשת הזמנות שהסטטוס שלהן `pending`/`failed` **אבל יש להן `transaction_id`**.

### אם יש תוצאות — זו התקלה

**המשמעות:** הלקוחות שילמו בפועל. חברת הסליקה קיבלה את הכסף והחזירה מזהה עסקה. אבל ההודעה שאמורה לעדכן את ההזמנה (**callback / IPN / webhook**) לא הגיעה לאתר או נדחתה.

זו התקלה הכי נפוצה, הכי יקרה, והכי לא מורגשת: הלקוח חויב, המוצר לא נשלח.

**הסיבות, לפי סדר השכיחות:**

1. **חומת אש או תוסף אבטחה חוסמים את קריאת ה-callback.**
   Wordfence / iThemes / All-In-One Security / Cloudflare WAF רואים בקשת POST מכתובת IP לא מוכרת, בלי קוקיז ובלי User-Agent של דפדפן — ומסווגים אותה כבוט.
   **בדיקה:** ביומן החסימות של תוסף האבטחה, לחפש חסימות בזמנים שמתאימים להזמנות התקועות. ב-Cloudflare: Security → Events, לסנן לפי הנתיב `/wc-api/`.
   **תיקון:** להוסיף את טווחי ה-IP של חברת הסליקה ל-allowlist, ולהחריג את הנתיב `/wc-api/*` מכל חוקי ה-WAF וה-Rate Limiting.

2. **כתובת ה-callback המוגדרת אצל ספק הסליקה שגויה.**
   קורה אחרי מעבר דומיין, מעבר מ-http ל-https, מעבר משרת, או שינוי מבנה קישורים.
   **בדיקה:** להיכנס לממשק הניהול של חברת הסליקה ולהשוות את כתובת ה-callback לכתובת שהתוסף מצפה לה (מופיעה בהגדרות התוסף בווקומרס).
   **תיקון:** לעדכן לכתובת הנוכחית המדויקת, כולל `https://` וכולל/ללא `www` בדיוק כמו ב-`siteurl`.

3. **הפניה (redirect) שוברת את ה-POST.**
   אם ה-callback מגיע ל-`http://nama-c.com/...` והשרת מפנה ל-`https://www.nama-c.com/...`, הפניית 301 **הופכת POST ל-GET ומאבדת את גוף הבקשה**. השער "מדווח" והאתר מקבל בקשה ריקה.
   **בדיקה:**
   ```bash
   curl -sSI -X POST "http://nama-c.com/wc-api/<gateway>" | head -20
   curl -sSI -X POST "https://nama-c.com/wc-api/<gateway>" | head -20
   ```
   כל תגובת 301/302 כאן היא הבעיה.
   **תיקון:** לתת לספק הסליקה את הכתובת הקנונית הסופית, כך שלא תהיה שום הפניה.

4. **תעודת SSL לא תקינה או שרשרת חסרה.**
   דפדפנים סלחניים, שרתים לא. אם שרשרת התעודות חסרה ביניים, שרת הסליקה יסרב להתחבר.
   **בדיקה:** `openssl s_client -connect nama-c.com:443 -servername nama-c.com < /dev/null 2>&1 | grep -i verify`
   **תיקון:** להתקין את שרשרת התעודות המלאה (fullchain).

5. **תור Action Scheduler תקוע.**
   חלק מהשערים מעדכנים את ההזמנה דרך פעולה מתוזמנת. אם התור לא רץ, העדכון יושב בתור לנצח.
   **בדיקה:** בדיקה C1 ב-SQL, או `wp action-scheduler run --batch-size=50`. אם ההזמנות מתעדכנות פתאום — מצאת.

**השלמה של ההזמנות שכבר תקועות** (רק אחרי אימות מול דוח הסליקה שהכסף אכן התקבל):
```bash
wp wc order update <order_id> --status=processing --user=1
```
לעולם לא להריץ עדכון גורף לפני צילוב מול דוח העסקאות של חברת הסליקה.

## שלב 2: היכן בדיוק נשבר התהליך?

כאן נכנס `tools/nama-checkout-logger.php`. להתקין ב-`wp-content/mu-plugins/` ולהמתין 24–48 שעות לאיסוף נתונים.

הוא מתעד את המסלול המלא, ובמסך כל הזמנה מופיעה תיבה **"Nama — מסלול הצ׳קאאוט"**.

**קריאת המסלול:**

| מה רואים במסלול | המסקנה |
|---|---|
| `CHECKOUT_VIEW` ואין `CHECKOUT_SUBMIT` | הלקוח לא לחץ "בצע הזמנה" — נטישה, או שהכפתור לא עבד (ראה שלב 3) |
| `CHECKOUT_NONCE_INVALID` | **עמוד התשלום מוגש ממטמון.** ראה שלב 4 |
| `CHECKOUT_VALIDATION_FAILED` | שדה חובה נכשל בוולידציה. הפירוט ביומן מראה איזה |
| `ORDER_CREATED` ואין כלום אחריו | הלקוח לא הופנה לסליקה, או שלא חזר ממנה |
| `ORDER_CREATED_WITHOUT_GATEWAY` | הצ׳קאאוט נשבר לפני בחירת שיטת התשלום |
| `OUTBOUND_HTTP_FAILED` | **השרת לא מצליח לצאת אל שער הסליקה.** ראה שלב 5 |
| `FATAL_DURING_CHECKOUT` | שגיאת PHP באמצע התהליך. הקובץ והשורה ביומן |
| `CLIENT_JS_ERROR` / `CLIENT_WC_AJAX_ERROR` | שגיאה בדפדפן של הלקוח. ראה שלב 3 |

## שלב 3: שגיאות JavaScript בצ׳קאאוט

בצ׳קאאוט הקלאסי, לחיצה על "בצע הזמנה" היא קריאת AJAX. כל שגיאת JS לפניה — התהליך מת בשקט, בלי הודעה ללקוח.

**חשודים עיקריים:**
- **איחוד/דחיסה של JS** ע"י תוסף מטמון. `checkout.js` של ווקומרס וסקריפט של שער הסליקה מאוחדים לקובץ אחד וסדר הטעינה נשבר.
- **Defer / Delay JavaScript.** תכונות "טעינה מושהית עד אינטראקציה" (WP Rocket, Perfmatters, LiteSpeed) שוברות את הצ׳קאאוט באופן קבוע.
- **שני תוספי אופטימיזציה** שמעבדים את אותם קבצים.
- **תבנית RTL** שמשנה מבנה DOM שהסקריפט מצפה לו.

**בדיקה ידנית:**
1. לפתוח את עמוד התשלום בגלישה פרטית.
2. Console פתוח → למלא הזמנה אמיתית עד הסוף.
3. כל שגיאה אדומה ב-Console = חשוד.
4. בלשונית Network: הבקשה `?wc-ajax=checkout` — לוודא שהיא מחזירה **200** ו-**JSON תקין**. אם היא מחזירה HTML, 500, או JSON עם HTML לפניו — זו הסיבה.

**התיקון הסטנדרטי — להחריג את הצ׳קאאוט מכל אופטימיזציה:**

בתוסף המטמון, להוסיף לרשימת ההחרגות של JS/CSS Minify+Combine וגם ל-Delay JS:
```
woocommerce/assets/js/frontend/checkout
woocommerce/assets/js/frontend/add-to-cart
wc-checkout
wc-cart-fragments
jquery.blockUI
js.stripe.com
```
ובנוסף להחריג את כל הסקריפטים של תוסף הסליקה (לפי שם התיקייה שלו).

> **בדיקת זהב:** לכבות **את כל** תוספי המטמון והאופטימיזציה לשעה, ולבצע 3 הזמנות בדיקה. אם עברו חלק — מצאת את המשפחה. להדליק חזרה אחד-אחד.

## שלב 4: מטמון על עמודים דינמיים

עמודי **עגלה, תשלום, החשבון שלי** חייבים להיות מוחרגים ממטמון דפים לחלוטין. אם לא — לקוח מקבל HTML של מישהו אחר, עם `nonce` שכבר לא תקף.

התוצאה: "פג תוקף הסשן", עגלה שמתרוקנת, או הזמנה שנוצרת ונתקעת.

**החרגות נדרשות (נתיבים):**
```
/cart/           ועמוד העגלה בעברית אם ה-slug שונה
/checkout/
/my-account/
/*?add-to-cart=*
/*?wc-ajax=*
/wc-api/*
/*?removed_item=*
```

**החרגות נדרשות (קוקיז) — קריטי ופחות מוכר:**
```
woocommerce_items_in_cart
woocommerce_cart_hash
wp_woocommerce_session_
wordpress_logged_in_
```
כל בקשה שנושאת אחת מהן חייבת לעקוף את המטמון.

**ב-Cloudflare:** ליצור Cache Rule עם `Bypass cache` על הנתיבים למעלה. אם משתמשים ב-APO — לוודא שהאינטגרציה עם ווקומרס פעילה.

**אימות:**
```bash
curl -sSI https://nama-c.com/checkout/ | grep -iE 'cf-cache-status|x-cache|age'
```
כל תוצאה שאינה `BYPASS`/`DYNAMIC`/`MISS` היא תקלה.

## שלב 5: השרת לא מצליח לדבר עם שער הסליקה

חלק מהשערים עובדים ב-server-to-server: השרת שולח בקשה ל-API של הסליקה ומחכה לתשובה. אם השרת חסום ליציאה, ההזמנה נכשלת.

**בדיקה מהשרת עצמו (SSH):**
```bash
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://<domain-של-חברת-הסליקה>/
```

**חשודים:**
- חומת אש של השרת שחוסמת יציאה
- `allow_url_fopen` / cURL חסומים
- שרת ללא IPv4 יוצא תקין
- זמן תגובה איטי + `max_execution_time` נמוך → timeout באמצע הסליקה

**בדיקת loopback** (קריטית גם ל-WP-Cron):
```bash
curl -sS -o /dev/null -w "%{http_code}\n" https://nama-c.com/wp-cron.php
```
אם זה נכשל — WP-Cron לא רץ, וזו סיבה עצמאית להצטברות הזמנות pending.

## שלב 6: הקרון — למה ההזמנות נערמות לנצח

גם כשהנטישה טבעית, הזמנות pending אמורות להתבטל אוטומטית אחרי שעה. אם הן נערמות לנצח — הקרון לא רץ.

**שני תנאים חייבים להתקיים:**

1. **"שמירת מלאי (דקות)" מוגדר.**
   `WooCommerce → הגדרות → מוצרים → מלאי → Hold stock (minutes) = 60`
   ההגדרה הזו היא שמפעילה את המשימה `woocommerce_cancel_unpaid_orders`. אם היא ריקה — אף הזמנה לא תבוטל לעולם.

2. **הקרון בפועל רץ.**
   ```bash
   wp cron test
   wp cron event list --format=table | head -20
   ```
   כל משימה שה-`next_run_relative` שלה שלילי = איחור.

**המעבר לקרון אמיתי בשרת (מומלץ בכל חנות):**
```php
// wp-config.php
define( 'DISABLE_WP_CRON', true );
```
```cron
*/5 * * * * cd /path/to/site && /usr/bin/php wp-cron.php >/dev/null 2>&1
```

**Action Scheduler** — התור של ווקומרס — נבדק בנפרד:
```bash
wp action-scheduler run --batch-size=50
```
`WooCommerce → סטטוס → Scheduled Actions`. אם `Pending` בעשרות אלפים או שיש `Failed` רבות — התור חנוק. לנקות היסטוריה:
```bash
wp action-scheduler clean --batch-size=1000 --before='1 month ago'
```

## שלב 7: משלוח שלא זמין

תקלה שקטה ונפוצה: לקוח מזין כתובת שאין לה אזור משלוח מתאים. אין שיטת משלוח → אין סכום → כפתור התשלום לא עובד. הלקוח לא מבין למה, ונוטש.

**בדיקה:** `WooCommerce → הגדרות → משלוחים`. חייב להיות אזור לישראל עם לפחות שיטה אחת, **ובנוסף** אזור "שאר העולם" עם שיטת fallback.

**בדיקה מעשית:** להזין בצ׳קאאוט יישוב קטן/מיקוד לא שגרתי ולראות אם מופיעה שיטת משלוח.

## שלב 8: הגדרות שער הסליקה

- **Test / Sandbox mode כבוי?** שער במצב בדיקה לא סולק כסף אמיתי.
- **מפתחות API בתוקף?** מפתחות מתחלפים ופגים. `invalid signature` / `hash mismatch` ביומן = מפתח שגוי.
- **מטבע תואם?** אם ווקומרס ב-ILS והמסוף מוגדר ל-USD — כל עסקה תידחה.
- **תמיכה בסכומים עשרוניים?** חלק מהמסופים מצפים לאגורות (שלמים) ולא לשקלים עשרוניים.
- **3DS / אימות דו-שלבי:** תהליך OTP ארוך מגדיל נטישה. לבדוק ביומן כמה עסקאות נעצרות בשלב האימות.

**היכן קוראים:** `WooCommerce → סטטוס → יומנים`, ולבחור את הקובץ של השער.

## שלב 9: מעקב מתמשך

אחרי התיקון, לוודא שהתקלה לא חוזרת:

1. להשאיר את `nama-checkout-logger.php` מותקן.
2. פעם בשבוע להריץ את `tools/nama-cli-audit.sh` ולהשוות את שיעור ההזמנות הלא מושלמות.
3. להגדיר התראה: אם `pending` מעל 24 שעות עולה על סף מסוים — להודיע.
4. לצלב חודשית את דוח העסקאות של חברת הסליקה מול ההזמנות בווקומרס. פער = הזמנות ששולמו ולא עודכנו.

## סיכום: סדר החשודים לפי שכיחות

1. **callback חסום** ע"י חומת אש / כתובת שגויה / הפניה ששוברת POST — *הכי נפוץ, והכי יקר*
2. **קרון לא רץ** → הזמנות pending נערמות לנצח במקום להתבטל
3. **מטמון על עמוד התשלום** → nonce לא תקין
4. **שגיאת JS** מאיחוד/השהיית סקריפטים
5. **Action Scheduler תקוע**
6. **אין שיטת משלוח זמינה** לכתובת הלקוח
7. **מפתחות API פגי תוקף** בשער הסליקה
8. **שגיאה פטאלית ב-PHP** באמצע התהליך
