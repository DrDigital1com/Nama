## 2. 🆕 זיהוי סופי של מקור ה-403

**זה מתקן ממצא קודם שלי.** ב-`docs/09` §7 כתבתי שה-403 מגיע ממגביל קצב מובנה של
LiteSpeed או ModSecurity. **זו הייתה השערה, והיא הייתה לא מדויקת.**

הגורם הוא **cPGuard** — חומת אש מסחרית שמותקנת בשרת האחסון. עמוד ה-CAPTCHA
מצהיר על כך במפורש.

### למה זה משנה מעשית
| שיערתי | בפועל |
|---|---|
| להגדיר את LiteSpeed | **אין מה לחפש שם.** ההגדרה היא בלוח cPGuard, או דרך פנייה לאחסון |
| מגביל קצב אנונימי | מוצר אבטחה עם רשימות היתר, יומנים וממשק ניהול |

**הפעולה בשלב 0 בספר הפעולות עודכנה בהתאם:** יש להחריג ב-cPGuard את כתובות
ה-IP של טרנזילה ואת הנתיבים `/?wc-api=*` ו-`/?wc-ajax=*`.

זה מחזק מאוד את החשד מ-`docs/09` §5.2: אם cPGuard חוסם בקשות לפי קצב או לפי
מוניטין IP, **הוא יכול לחסום גם את הודעת התשלום של טרנזילה** — והתוצאה תהיה
בדיוק מה שרואים: תשלום שנגבה, הזמנה שנשארת `pending`, וביטול אוטומטי אחרי שעה.

## 3. מה שכן פתוח — ה-REST API

מיפיתי מה נחסם ומה לא:

| נקודת קצה | תשובה | מי חוסם |
|---|---|---|
| `/wp-login.php` | **403** (curl) · CAPTCHA (דפדפן) | **cPGuard** |
| `/wp-admin/authorize-application.php` | **403** | **cPGuard** |
| `/wp-json/` | **200** | — פתוח |
| `/wp-json/wc/v3` | **200** | — פתוח |
| `/wp-json/wp/v2/plugins` | 401 `rest_cannot_view_plugins` | **וורדפרס** — דורש אימות בלבד |
| `/wp-json/wp/v2/settings` | 401 | **וורדפרס** — דורש אימות בלבד |

**cPGuard חוסם רק את נתיבי ההתחברות. ה-REST API פתוח לגמרי.**

והכי חשוב — ניסיון אימות Basic עם הסיסמה הרגילה החזיר:

```json
{"code":"incorrect_password",
 "message":"The provided password is an invalid application password."}
```

ההודעה הזו מוכיחה ש-**Application Passwords מופעל באתר** ושנקודת הקצה מקבלת
אימות Basic. חסרה רק סיסמת יישום תקינה.

## 7. 🔴 cPGuard חסם לקוח לגיטימי — הדגמה חיה של המנגנון החשוד

במהלך ניסיונות ההתחברות ל-REST עם פרטים שגויים, cPGuard **חסם בהדרגה את כתובת
ה-IP שלי**. ההסלמה תועדה:

| שלב | `/` | `/wp-json/` | `/shop/` | `/wp-json/wc/v3` | REST עם אימות |
|---|---|---|---|---|---|
| התחלה | 200 | 200 | 200 | 200 | 401 (תשובת וורדפרס תקינה) |
| אחרי כמה ניסיונות כושלים | 200 | 200 | 200 | **403** | **403** |
| בהמשך | 200 | — | **403** | — | **403** |

**החסימה התפשטה מנקודות הקצה של האימות אל עמודי החנות הרגילים.** `/shop/` ועמוד
מוצר החזירו 403 לכתובת שלי, בזמן שדף הבית עדיין החזיר 200.

### למה זה חשוב הרבה מעבר לתקרית הזו

עד כה, הטענה ש-cPGuard עלול לחסום את הודעת התשלום של טרנזילה הייתה **השערה**
(`docs/09` §5.2, שלב 0 בספר הפעולות). היא התבססה על התאמה בין התסמין לבין
התנהגות אפשרית של חומת האש.

**עכשיו ראינו את ההתנהגות הזו קורית בפועל:** cPGuard חסם מקור לגיטימי, לפי
מוניטין שנצבר מבקשות קודמות, והרחיב את החסימה לנתיבים שלא היו קשורים לניסיונות
האימות.

זה בדיוק התרחיש שמייצר הזמנה ששולמה ובוטלה:

```
לקוח משלם בטרנזילה  →  שרת טרנזילה פונה ל-?wc-api=WC_Gateway_Tranzila
                     →  cPGuard מחזיר 403
                     →  ההזמנה נשארת pending
                     →  "שמירת מלאי" מבטלת אותה אחרי 60 דקות
                     →  ההזמנה נספרת כ-cancelled מבין 867
```

### הבדיקה שתכריע — 30 שניות
**cPanel → cPGuard → Blocked IPs.**

**אם מופיעות שם כתובות של טרנזילה — זו התשובה לכל החקירה**, וגם ההסבר לפער בין
811 ההזמנות שהושלמו ל-867 שבוטלו. כדאי גם להסתכל ביומני cPGuard לאחור.

> **הבהרה:** החסימה הזו הייתה על כתובת ה-IP שלי בלבד. לקוחות אמיתיים מגיעים
> מכתובות אחרות ולא הושפעו. דף הבית המשיך להחזיר 200 לאורך כל התקרית.

### שינוי עדיפות
שלב 0 בספר הפעולות עולה מ"כדאי לבדוק" ל**עדיפות ראשונה**, לפני תיקון המיילים.
הבדיקה עצמה היא צפייה ברשימה — היא לא משנה כלום ולא מסכנת כלום.

`tools/wp-rest-audit.mjs` כתוב ובדוק. ברגע שתגיע סיסמת היישום:

```bash
WP_USER=audit WP_APP_PASS='xxxx xxxx xxxx xxxx xxxx xxxx' \
  node tools/wp-rest-audit.mjs
```

**הסקריפט קורא בלבד — הוא לא משנה, לא מוחק ולא מכבה כלום.**

מה שהוא בודק, לפי סדר:

| 1 | אימות | מבדיל בין 401 (סיסמה לא תקינה) ל-403 (cPGuard חוסם) |

| 3 | אותו דבר על הזמנות שנכשלו | 123 הזמנות נוספות |
