# שלב 0 — 🆕 חסימת 403 והקולבק של טרנזילה

**נוסף אחרי המדידה החיה.** זול, מהיר, ומכוון ישירות ל-867 ההזמנות שבוטלו.
פרטים מלאים: `docs/09-live-measurement-2026-08-30.md` §5.2 ו-§7.

## המצב
**א. השרת מחזיר 403 בקצב בקשות גבוה.** בסדרה של 10 בקשות רצופות מאותו IP,
3 חזרו `403 Forbidden`.

> ✅ **הגורם זוהה סופית: cPGuard.** בניסיון התחברות ל-`wp-admin` התקבלה הפניה
> ל-`recaptcha.cloud` עם ההודעה *"You are here because the url you are trying to
> access is protected by **cPGuard**"*. כלומר ה-403 אינו מגיע מ-LiteSpeed עצמו
> אלא מ-**cPGuard — חומת אש שמותקנת אצל האחסון**.
>
> **זה משנה את הפעולה הנדרשת:** אין מה לחפש הגדרות ב-LiteSpeed. יש לפנות
> לאחסון (או ללוח cPGuard ב-cPanel) ולהחריג שם את:
> - כתובות ה-IP של **טרנזילה** — כדי שהודעת התשלום לא תיחסם
> - הנתיבים `/?wc-api=*` ו-`/?wc-ajax=*`
>
> cPGuard חוסם גם את `/wp-login.php` (403 ל-curl, CAPTCHA לדפדפן).

לקוחות רגילים ברובם לא נפגעים: הקבצים הסטטיים מגיעים מקצה Cloudflare
(`cf-cache-status: HIT`, `max-age=31536000`) ולא נוגעים בשרת. **מה שכן מגיע לשרת
בכל פעם, בלי מטמון לעולם:**

- `?wc-ajax=get_refreshed_fragments` — בכל טעינת עמוד
- `?wc-ajax=update_order_review` — בכל שינוי שדה בצ׳קאאוט
- `?wc-ajax=checkout` — שליחת ההזמנה
- **`?wc-api=WC_Gateway_Tranzila` — הודעת התשלום מטרנזילה**

**ב. הקולבק של טרנזילה איטי.** נקודת הקצה זוהתה ונמדדה. גם מסלול הדחייה שלה
לוקח **2.0–2.3 שניות**, והיא מחזירה **HTTP 500** בכשל (`wp_die`).

## למה זה משנה
אם שרת של טרנזילה מקבל 403, או מוותר בגלל timeout לפני שהאתר עונה —
**התשלום נגבה, ההזמנה נשארת `pending`, ואחרי 60 דקות "שמירת המלאי" הופכת אותה
ל-`cancelled`.** זה בדיוק הפרופיל של 867 ההזמנות שבוטלו.

> זו **השערה שצריך לאמת**, לא ממצא מוכח. בקשה ריקה *אמורה* להידחות, ולא נבדקה
> קריאה אמיתית מטרנזילה (זיוף קריאת תשלום על חנות חיה משנה מצב הזמנות אמיתיות).
> אבל הבדיקה זולה והתסמין מתאים במדויק.

## 🔴 קודם כול — בדיקה של 30 שניות
**cPanel → cPGuard → Blocked IPs.**

**אם מופיעות שם כתובות של טרנזילה — זו התשובה לכל החקירה.**

הבדיקה הזו עלתה לעדיפות ראשונה אחרי שנצפה ש-cPGuard **חוסם בפועל לקוחות
לגיטימיים**: במהלך העבודה הוא חסם את כתובת ה-IP שלי, והחסימה התפשטה מנקודות
הקצה של האימות עד ל-`/shop/` ולעמודי מוצר. זו כבר לא השערה על מה שהוא *עלול*
לעשות. ראה `docs/12-admin-access-2026-08-30.md` §7.

## התיקון
1. **לפנות לאחסון** ולשאול: *"מה מפעיל 403 בשרת שלנו ומה הסף? מדובר ב-LiteSpeed
   anti-DDoS, ב-ModSecurity או במגביל קצב אחר?"*
2. **להחריג מהחסימה:**
   - את כתובות ה-IP של טרנזילה (לבקש מטרנזילה את הרשימה העדכנית)
   - את הנתיבים `/?wc-api=*` ו-`/?wc-ajax=*`
3. **לבקש מטרנזילה** את ערך ה-timeout שהם נותנים לקולבק, ולהשוות ל-2.3 השניות
   שנמדדו. שלב 3 (Redis) אמור לצמצם את הזמן הזה משמעותית.
4. **להפעיל את יומן טרנזילה** — `WooCommerce → סטטוס → יומנים → tranzila-*`.
   זה עדיין הפריט הפתוח מ-`docs/06` §10 סעיף 3.

## אימות
```bash
# אמור לחזור 200 בכל 10 הפעמים, בלי אף 403
for i in $(seq 1 10); do
  curl -s -o /dev/null -w "%{http_code} " https://nama-c.com/
done; echo
```
ואחרי הזמנת בדיקה אמיתית: לוודא שההזמנה עברה ל-`processing` מיד, ולא נשארה
`pending`.

# שלב 2 — OPcache מלא

**המצב:** 127.98MB בשימוש, **0.02MB פנוי**, hit rate 58.2%. הזיכרון גמור, 42% מהבקשות מקמפלות PHP מחדש.

> ⚠️ **הפירוק המעמיק הפך את השלב הזה למשתלם ביותר ברשימה.**
> נמדד חי: עמוד **404** — בלי ווקומרס, בלי עגלה, בלי מוצר — לוקח **2,751ms**.
> `admin-ajax.php` עם פעולה שלא קיימת מחזירה **בית אחד** אחרי **2,430ms**.
> עגלה ריקה: **2,402ms**. כלומר **‎~2.4 שניות הן טעינת PHP של 30 תוספים**, ותו לא.
>
> hit rate של 58.2% אומר ש-**42% מהבקשות מקמפלות מחדש את כל ערימת התוספים**.
> זה ההסבר הישיר ל-2.4 השניות — ותיקון של 10 דקות.
> ראה `docs/10-deep-dive-2026-08-30.md` §1 ו-§3.

## התיקון
**cPanel → MultiPHP INI Editor → Editor Mode** → לבחור את הדומיין → להוסיף/לעדכן:

```ini
opcache.enable=1
opcache.memory_consumption=512
opcache.interned_strings_buffer=64
opcache.max_accelerated_files=50000
opcache.revalidate_freq=2
opcache.validate_timestamps=1
opcache.save_comments=1
opcache.max_wasted_percentage=10
```

> `memory_consumption=512` ולא 256: 30 תוספים + WPML + Elementor + Woodmart מגיעים בקלות מעל 128MB, ואת זה כבר ראינו במדידה.

אם אין MultiPHP INI Editor — לפנות לתמיכת האחסון עם הבלוק הזה. זו בקשה שגרתית.

## אימות
להריץ שוב `/wp-admin/?nama_audit=1` ולהסתכל במקטע 1:
- **יעד:** hit rate מעל 97%, ו"פנוי" מעל 100MB
- אם hit rate עדיין נמוך אחרי יממה — להעלות ל-768MB

# שלב 3 — Redis Object Cache (התיקון לצ׳קאאוט של 4.5 שניות)

**המצב:** עמוד תשלום 4,454ms, עגלה 2,914ms, מול 96ms בדף הבית.

עמודי עגלה/תשלום דינמיים ולא נהנים ממטמון דפים. רק Object Cache עוזר להם.

> ✅ **המדידה החיה מחזקת את השלב הזה.** נמדד מבחוץ, עם סשן ועגלה אמיתית:
> `/checkout/` **3,563–4,053ms** מול **~280ms** בדפי הקטלוג — פי 13.
>
> והראיה החזקה ביותר: **עגלה ריקה כבר לוקחת 2,664ms.** אין בה מוצרים ואין מה
> לחשב — כל הזמן הזה הוא טעינת התוספים בלבד. זה בדיוק מה ש-Object Cache פותר.
>
> נמצא גם שסף כשל קרוב יותר משנראה: `get_refreshed_fragments` — הקריאה שרצה
> **בכל טעינת עמוד באתר** — לוקחת **2,283–2,873ms** כדי להחזיר 1.4KB, מול
> `"request_timeout":"5000"` שווקומרס מגדירה לה. מרווח של פי 2 בלבד, על שרת פנוי.
> ראה `docs/09-live-measurement-2026-08-30.md` §2.3.

## התיקון
1. **לוודא ש-Redis זמין:** cPanel → לחפש "Redis". אם אין — לפתוח פנייה לאחסון: *"אני צריך Redis server + PHP redis extension עבור הדומיין nama-c.com"*.
2. להתקין את התוסף **Redis Object Cache** (Till Krüss).
3. ב-`wp-config.php`, **לפני** השורה `/* That's all, stop editing! */`:
   ```php
   define( 'WP_REDIS_HOST', '127.0.0.1' );
   define( 'WP_REDIS_PORT', 6379 );
   define( 'WP_REDIS_DATABASE', 0 );
   define( 'WP_REDIS_PREFIX', 'namac_' );
   define( 'WP_REDIS_MAXTTL', 86400 );
   ```
   > `WP_REDIS_PREFIX` הוא חובה — יש עוד התקנה על השרת (טבלאות `wpq5_`). בלי קידומת שונה שני האתרים ידרסו זה את המטמון של זה.
4. **Settings → Redis → Enable Object Cache**

## אימות
- בתוסף: Status = Connected, Hit Ratio מעל 90% אחרי יום
- להריץ שוב את האודיט: מקטע 6 — **יעד: עמוד תשלום מתחת ל-800ms**
- **מיד אחרי ההפעלה: לבצע הזמנת בדיקה.** Object Cache שגוי יכול לשבור סשנים של עגלה.

## אם אין Redis באחסון
אין תחליף אמיתי. מה שכן אפשר לעשות בינתיים:
- לכבות תוספים שלא בשימוש (ראה שלב 8)
- להשתמש ב-WP Rocket → Preload כדי לחמם עמודים סטטיים

# שלב 4 — ניקוי בסיס הנתונים

**המצב:** `wpgh_options` מכילה 15.3MB נתונים ו-**427MB שטח מבוזבז**. הטבלה נקראת בכל בקשה.

> **אחרי גיבוי בלבד, בשעת עומס נמוכה.** הפקודות ב-`sql/cleanup.sql`.

```sql
-- 1. לשחרר את השטח המבוזבז (הפעולה הכי משמעותית)
OPTIMIZE TABLE wpgh_options;

-- 2. transients פגי תוקף
DELETE FROM wpgh_options
WHERE option_name LIKE '\_transient\_timeout\_%'
  AND option_value < UNIX_TIMESTAMP();

-- 3. סשנים שפג תוקפם
DELETE FROM wpgh_woocommerce_sessions WHERE session_expiry < UNIX_TIMESTAMP();
```

ואם יש WP-CLI:
```bash
wp transient delete --expired
wp action-scheduler clean --batch-size=1000 --before='1 month ago'
wp db optimize
```

**שרידים למחיקה** — רק אחרי אימות שהתוסף באמת לא בשימוש:
- `wpgh_hustle_tracking` (18,138 שורות) — תוסף Hustle אינו פעיל
- טבלאות בקידומת `wpq5_` — התקנה אחרת. **לוודא מול האחסון שאין אתר חי שמשתמש בהן.**

> **מניעת חזרה:** אחרי שלב 3, ה-transients יישמרו ב-Redis ולא ב-`wp_options`. זה מונע את הצטברות הבלגן מחדש.

להריץ את האודיט: מקטע 7 — עודף אמור לרדת מ-571MB לפחות מ-20MB.

curl -s https://nama-c.com/shop/ | grep -c 'rel="canonical"'
```

בנוסף: לוודא שמופיע `<h1>` ושפירורי הלחם מציגים "בית ← חנות".

1. **לפני הכל — לבדוק אם הכבדות בכלל בשימוש.** קבצי `shutterstock_*` בגודל 14–21MB הם כמעט תמיד מקור שהועלה בטעות. אם לא בשימוש — למחוק (חוסך מאות MB).

3. הגדרות: **Lossy**, המרה אוטומטית ל-**WebP**, הגשה עם `<picture>`, וגם שינוי גודל מקסימלי ל-**2048px**.
4. להריץ **Bulk Optimize** על כל ספריית המדיה.
5. ב-**WP Rocket → Media**: לוודא ש-LazyLoad פעיל לתמונות.

> יש כבר 116 קבצי WebP — כלומר ההמרה קיימת חלקית ולא הורצה על הכל.

## אימות
PageSpeed Insights על עמוד מוצר — **יעד LCP מתחת ל-2.5 שניות**.

> נמדד חי: **אין ולו תג `<picture>` אחד בכל האתר** — כלומר אין הגשת WebP.
> תמונות המוצר מוגשות `.jpg`. אחרי ShortPixel צריך להופיע `<picture>`:
> ```bash
> curl -s https://nama-c.com/product/wearable-breast-pump/ | grep -c '<picture'
> # לפני: 0   |  אחרי: > 0
> ```
> תיקון של דקה שכדאי לעשות בדרך: `namalogo-scaled.png` — לוגו PNG של 60KB.
> וכן: 49 מתוך 50 התמונות בדף הבית מסומנות `loading="lazy"`, כולל כנראה
> תמונות שמעל הקיפול. זה פוגע ב-LCP במקום לעזור.

# שלב 7 — WP Rocket: להפעיל מיזעור, עם החרגות הצ׳קאאוט

**המצב היום תקין:** `cf-cache-status: DYNAMIC` על עגלה ותשלום — Cloudflare לא מגיש אותם ממטמון. **לא לשנות את זה.**
אומת חי מול סשן עם עגלה מלאה: `/cart/`, `/checkout/` ו-`/my-account/` כולם
`DYNAMIC` עם `cache-control: no-cache, private`. **אין מה לתקן כאן.**

> ⚠️ **תוקן אחרי מדידה חיה — הפעולה הפוכה ממה שנכתב כאן במקור.**
> השלב הזה נכתב מתוך הנחה שהמיזעור פועל וצריך רק להחריג ממנו קבצים.
> בפועל **המיזעור והאיחוד כבויים לגמרי**: אין ולו חתימת `data-rocket-*` אחת,
> ונספרו **78 קובצי JS ו-78 קובצי CSS נפרדים בעמוד התשלום** (בדף הבית 78 ו-96).
> מטמון הדפים של WP Rocket כן עובד — הוא זה שמסביר 280ms בקטלוג מול 3,600ms בצ׳קאאוט.
>
> לכן: **להפעיל** את WP Rocket → File Optimization, **ובאותה פעולה** להזין את
> ההחרגות שלמטה. ההחרגות נכונות ונחוצות — הן פשוט מיועדות למצב שעדיין לא הופעל.
>
> **להריץ ב-staging תחילה.** הפעלת מיזעור על WPML + YayCurrency + Elementor +
> Woodmart היא פעולה שיכולה לשבור עיצוב, ואחריה חובה הזמנת בדיקה מלאה.

ההחרגות שיש להזין ב-**WP Rocket → File Optimization**, ברשימות של Minify/Combine ושל Delay JavaScript:

```
woocommerce/assets/js/frontend/checkout
woocommerce/assets/js/frontend/add-to-cart
wc-checkout
wc-cart-fragments
jquery.blockUI
WCGatewayTranzila
```

ו-**WP Rocket → Advanced Rules → Never Cache URLs**:
```
/cart/
/checkout/
/my-account/
```

> WP Rocket מזהה ווקומרס ומחיל חלק מזה אוטומטית — אבל עם WPML + YayCurrency + טרנזילה כדאי לוודא ידנית.

## אימות
```bash
curl -sSI https://nama-c.com/checkout/ | grep -i cf-cache-status
```
צריך להחזיר `DYNAMIC` או `BYPASS`. **לעולם לא `HIT`.**
