# שערי סליקה ישראליים — מה לבדוק בכל אחד

> מסמך זה מתאר **מה לבדוק**, לא ערכים ספציפיים. כתובות ה-callback, טווחי ה-IP ומבני הבקשות משתנים בין ספקים ובין גרסאות תוסף — יש לאמת כל פרט מול התיעוד העדכני של הספק ומול ממשק הניהול שלו.

שערים נפוצים בשוק הישראלי: **Tranzila, CardCom, PayPlus, Meshulam/Grow, Yaad Sarig, iCredit, Pelecard, Isracard, Nayax, PayMe**, ולצידם **Bit** ו-**PayBox** כשיטות תשלום נוספות.

---

## המאפיין שמייצר את רוב התקלות

כמעט כל השערים הישראליים עובדים ב-**redirect**: הלקוח עוזב את האתר, משלם בעמוד של חברת הסליקה, וחוזר. זה יוצר שתי נקודות כשל שלא קיימות בשער מוטמע:

1. **הלקוח לא חוזר** — סגר את החלון, נפל לו האינטרנט, או ה-OTP לקח יותר מדי זמן. ההזמנה נשארת `pending`.
2. **ה-callback לא מגיע** — חברת הסליקה שולחת הודעת server-to-server על תשלום מוצלח, אבל היא נחסמת. **הלקוח שילם, ההזמנה לא עודכנה.**

מקרה 2 הוא היקר ביותר, והוא זה שבודקים בבדיקה **A7** ב-`sql/orders-diagnostics.sql`.

## רשימת בדיקה לכל שער

### 1. כתובת ה-callback
- מה הכתובת המוגדרת **בממשק של חברת הסליקה**?
- מה הכתובת שהתוסף **מצפה** לה (מופיעה בהגדרות התוסף בווקומרס)?
- האם הן זהות **בדיוק** — כולל `https://`, כולל/ללא `www`, כולל הסלאש בסוף?

**הבדיקה הקריטית — האם יש הפניה?**
```bash
curl -sSI -X POST "http://nama-c.com/wc-api/<gateway>"      | head -5
curl -sSI -X POST "https://www.nama-c.com/wc-api/<gateway>" | head -5
```
כל `301`/`302` כאן שובר את ה-callback: הפניה הופכת POST ל-GET ומאבדת את גוף הבקשה. השער "מדווח", האתר מקבל בקשה ריקה.

### 2. חסימה ע"י אבטחה
קריאת callback נראית לחומת אש כמו בוט: POST מ-IP לא מוכר, בלי קוקיז, בלי User-Agent של דפדפן.

- **ביומן החסימות** של תוסף האבטחה — האם יש חסימות בזמנים שמתאימים להזמנות התקועות?
- **ב-Cloudflare**: Security → Events, סינון לפי הנתיב `/wc-api/`.
- **תיקון:** להוסיף את טווחי ה-IP של הספק ל-allowlist (לבקש מהם רשימה מעודכנת), ולהחריג את `/wc-api/*` מכל חוקי WAF ו-Rate Limiting.

### 3. מפתחות ותעודות
- מפתחות API / Terminal ID / מפתח חתימה — **בתוקף**?
- `invalid signature` / `hash mismatch` ביומן = מפתח שגוי או שיטת חתימה שהשתנתה.
- תעודת SSL עם **שרשרת מלאה**:
  ```bash
  openssl s_client -connect nama-c.com:443 -servername nama-c.com < /dev/null 2>&1 | grep -i 'verify'
  ```
  שרשרת חסרה — דפדפנים סלחניים, שרתי סליקה לא.

### 4. מטבע וסכומים
- ווקומרס ב-**ILS** והמסוף מוגדר ל-ILS?
- חלק מהמסופים מצפים לסכום **באגורות (מספר שלם)**. אי-התאמה = דחייה של כל עסקה.
- תשלומים (קרדיט) — מספר התשלומים שנשלח נתמך במסוף?

### 5. מצב בדיקה
`Test` / `Sandbox` **כבוי**? שער במצב בדיקה יוצר הזמנות שלעולם לא ייסלקו.

### 6. חשבונית ומע"מ
תוספי חשבונית ישראליים (חשבונית ירוקה, iCount, Rivhit, EZcount) נקראים לרוב ב-`woocommerce_payment_complete`. אם התוסף נכשל או נתקע ב-timeout — התהליך יכול להישבר **אחרי** שהתשלום עבר.
בדיקה: `WooCommerce → סטטוס → יומנים`, ובדוח האודיט מקטע 5 (Action Scheduler failed hooks).

### 7. יומנים
כל תוסף סליקה רציני כותב יומן. להפעיל **Debug/Logging** בהגדרות התוסף, ולקרוא ב-`WooCommerce → סטטוס → יומנים`.

מה לחפש:
| מחרוזת | משמעות |
|---|---|
| `declined` / `refused` | הכרטיס נדחה — לא תקלה טכנית |
| `timeout` | השרת לא מצליח לצאת אל השער, או שהשער איטי |
| `invalid signature` / `hash` | מפתח שגוי או פג |
| `callback` / `IPN` | מעקב אחרי הודעות נכנסות |
| `SSL` / `certificate` | בעיית תעודה |

## Bit ו-PayBox

שיטות התשלום האלה עוברות דרך אפליקציה בנייד, מה שמאריך את התהליך:
1. הלקוח מופנה לעמוד סליקה
2. סורק QR או עובר לאפליקציה
3. מאשר באפליקציה
4. חוזר לאתר

בכל אחד מהשלבים הלקוח עלול לא לחזור. **שיעור `pending` גבוה יותר בשיטות האלה הוא נורמלי** — אבל שיעור גבוה **בלי** callback שמגיע אחר כך הוא תקלה.

בדיקת ההפרדה: להריץ את בדיקה **A3** ב-SQL ולהשוות את שיעור ה-`incomplete_pct` בין שיטות התשלום. אם שיטה אחת חורגת דרמטית מהשאר — התקלה בשיטה הזו, לא בצ׳קאאוט הכללי.

## תרחיש הבדיקה המלא

לפני שמכריזים "תוקן", לבצע לכל שער פעיל:

1. הזמנה שמסתיימת בהצלחה → מוודאים `processing`
2. הזמנה שנדחית בכוונה (כרטיס בדיקה שנדחה) → מוודאים `failed` **עם הודעה ברורה ללקוח**
3. הזמנה שננטשת בעמוד הסליקה (סוגרים את החלון) → מוודאים `pending`, ושהיא **מתבטלת אוטומטית** לאחר זמן שמירת המלאי
4. הזמנה מנייד — התהליך שונה מהותית בדסקטופ
5. הזמנה כאורח **וגם** כמשתמש מחובר

בכל אחת מהן לפתוח את תיבת **"Nama — מסלול הצ׳קאאוט"** בהזמנה ולוודא שהמסלול מלא עד `PAYMENT_COMPLETE`.
